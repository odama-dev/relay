# Decisions & deviations — Odama OS

Choices made while building Phase 1 (`PRD/PRD-Fase-1-MVP.md`) that aren't
obvious from the code. Newest section last.

## Pivot (13 Oct 2026)

- **Onweekend OS → Odama OS.** The previous Company OS codebase was repurposed:
  its design system, shell and shared components stay; every domain module
  (finance, BI/Hermes, HR external talent, services, engagements, demo DB) and
  all old migrations were removed. Phase 1 starts from an empty database, except
  clients and projects imported from CSV (PRD).

## Data layer & access control

- **Prisma + RLS.** Prisma 6 owns the schema and migrations; the access matrix is
  enforced by Postgres Row Level Security. `withRls()` (`lib/db.ts`) runs each
  user request in a transaction as `authenticated` with the user's JWT claims, so
  the same policies apply to the app and to direct Supabase API calls. The system
  connection (migration owner) bypasses RLS and is reserved for auth, webhooks,
  jobs, notifications and audit (see `CLAUDE.md`).
- **Helpers in a private `app` schema**, not `public`, so PostgREST doesn't expose
  them as RPC. `current_role()` from the PRD is `app.user_role()` — `current_role`
  is a reserved SQL word. `app.uid()` reads `request.jwt.claims` itself, so the
  migrations also run on plain Postgres (roles are created if missing).
- **Column-level secrecy → separate tables.** RLS works per row, but the matrix
  hides *columns*: the contract value (Designer & Dev, HR, other PMs) and the hour
  budget (HR). They live in `project_contracts` and `project_budgets` (1:1 with
  `projects`), each with its own policies.
- **Guards as triggers.** Rules that RLS can't express per column are triggers
  that only bite through RLS (`app.via_rls()`): a user can't change their own
  role/admin flag; only the project's PM reviews out-of-scope work; locked weeks
  can't be edited; a sent invoice can only be voided; deleted comments keep their
  text and record who deleted them.
- **Privileged transitions are system actions after an RLS check.** Issuing an
  invoice number, creating Xendit links, recording payments and applying an
  approved time correction run on the system connection, after the user's right
  to do it was proven under RLS (e.g. the correction review itself is an RLS
  update that only the reviewer can make).
- **Aggregates for health** (usage over everyone's time) are computed on the
  system connection after checking the viewer may read the project's budget —
  Designer & Dev may see health but not other people's time entries.
- **Storage:** private buckets, no storage policies. Files are served only by
  app routes that check access under RLS and redirect to a 60-second signed URL.
  Without Supabase, files go to `./.data/storage` (dev only).
- **PM definitions.** "PM project" = the project's `pm_id`. A user with the PM
  role who is only a member can edit project info (matrix "E (M)") but sections,
  members, task deletion and out-of-scope review belong to the project's PM and
  C-Level (`app.can_manage_project`). PM-role users see every project but only
  the tasks/time/contract value of projects they're on.
- **Sales on tasks:** the matrix gives Sales "L (M)" on section & task, so Sales
  members read tasks and comment but don't create or edit them (M2.2's "all
  members can create" is read together with the matrix).

## M0 — Foundation

- **Invitations are app tokens, not Supabase invite links.** Supabase email OTPs
  expire after at most a day; the PRD wants 7 days. The admin API creates the
  auth user (no password), the app emails its own 7-day link
  (`user_invitations`, only a SHA-256 of the token is stored), and accepting it
  sets the password and activates the profile. Resending revokes older links.
- **Password reset** uses a Supabase recovery link generated by the admin API and
  sent through Resend, so every account email shares one template and sender.
- **Deactivation** sets the profile to `deactivated` (it stops resolving on the
  next request) and bans the Supabase user so no session can refresh.
- **Bootstrap admin:** an `ADMIN_EMAILS` address signing in without a profile
  becomes an active C-Level admin; `scripts/create-admin.mjs` sets one up with a
  password on a fresh environment.
- **Notifications:** `notify()` sends a Slack DM when the user is linked, and
  always writes `notification_log`, which doubles as the in-app inbox (bell). Users
  can mute the work-chatter types; approvals, payments and invoice notices can't
  be muted.

## M1 — Client & Project

- **Project code** is assigned by a trigger under an advisory lock (no duplicate
  numbers under concurrency); kind and client are fixed after creation. A client
  code `INT` is reserved for internal projects.
- **Retainer rollover history** is kept in `retainer_periods`: a settings change
  first freezes every past month with the old settings, and the 1st-of-month job
  freezes the month that just ended. Usage is never frozen — late corrections
  still count. Carry-over from month M uses month M's mode (the mode applies "from
  the current month"), and is never negative.
- **Budget alerts** fire once per threshold per period (`project_alerts`, unique);
  thresholds the project falls back under are re-armed. Checked after every time
  change, budget change, and hourly by the `budget-alerts` job.
- **CSV import** runs on the system connection (admin only, one-off migration).
  Template headers may carry the PRD's `*` marker. Users are created as
  `invited`; "Send invitations" emails them afterwards.

## M2 — Task

- `tasks.position` is a float (fractional ordering) so a drag rewrites one row.
  The same order is used inside kanban columns.
- Comment bodies are `{ text, mentions[] }` — plain text with `@Full Name`
  mentions resolved against project members (longest name first) and light
  inline formatting (`**bold**`, `_italic_`, links) rendered safely. Task
  descriptions are validated Tiptap JSON; images must point at our own storage
  route.

## M3 — Time Log

- `minutes` is the stored unit; durations accept `1h 30m`, `1.5`, `1,5`, `1:30`,
  `90m`, `2 jam`. No minimum unit.
- Week lock is a row in `timesheet_locks` (Monday). Through RLS, entries of a
  locked week can't be created, changed or deleted; corrections are applied by
  the system after the reviewer approves.
- Out-of-scope review fields can only be changed by the project's PM / C-Level
  (trigger); the owner may flag/unflag until it's reviewed.

## M4 — Project Health

- Status: On track below the first threshold, Warning from the first threshold up
  to 100% inclusive, Over budget above 100%. Alerts fire when usage *reaches* a
  threshold.
- The overview sorts by a risk score: status first, then usage, overdue tasks and
  waiting out-of-scope entries.

## M5 — Invoice & Payment

- **Invoice number** is taken on the first send (from `app.next_invoice_number`,
  a row-locked yearly counter) and kept if that send fails, so a retry reuses it.
  Numbers already in use are skipped — e.g. ones issued before Odama OS (PRD open
  question 2: set the starting point by inserting into `invoice_sequences`).
- A draft that already got a number (failed send) can only be voided, never
  deleted, so no number disappears.
- **PDF template** is a parameterized HTML placeholder
  (`components/invoice/invoice-document.tsx`) until the studio's Figma template is
  converted (PRD open question 4). PDFs are printed by headless Chrome and stored
  in the `invoices` bucket.
- **Xendit currency** (open question 1): links are created in the invoice
  currency. `settlement_amount_idr` and the FX rate are filled from the callback's
  settlement fields when Xendit sends them; otherwise they stay empty for Finance
  to review. Confirm with the Xendit account before go-live.
- Without Xendit keys outside production, payment links open `/dev/pay/<id>`, a
  local checkout simulator that posts a correctly signed webhook (incl. a
  "send twice" button for the idempotency check).
- Recipients default to the client's billing email + primary contact. The email
  subject may use `{number}`, filled in at send time.

## Dashboard per role (2026-10-16)

Spec: `PRD/OVERVIEW-SPEC.md`. `/dashboard` is the home screen (`/` redirects
there); the card set follows `profiles.role`, `is_admin` doesn't change it.

- **Queries in app code, under RLS — not views.** The spec suggests database
  views / RPCs for the heavy aggregates. Every card instead reads through
  `asUser` (`lib/dashboard/queries.ts`), so the same policies apply; health
  reuses `computeHealth` after the budgets were read under RLS, exactly like
  Project Health. The one exception is **HR-3 (tasks per person)**: HR can't read
  tasks, so `app.task_summary_per_person()` (migration `…_dashboard`, `SECURITY
  DEFINER`) returns counts only, and only to HR, C-Level and admins — tested in
  `tests/rls/access.test.ts`.
- **One slot per card.** Each card (`app/(app)/dashboard/card.tsx`,
  `defineCard`) has its own Suspense skeleton and turns a failed load into its
  error state with "Try again", so one card never takes the page down.
- **Past workdays only.** DD-2 and HR-1 flag workdays *before today* without
  time ("hari kerja yang sudah lewat"); the compliance page (M3.7) still counts
  today.
- **Currencies are never converted**, so where the spec says "largest" across
  currencies: CL-1 lists the 5 *longest-overdue* requests, and FN-4 ranks clients
  by their IDR amount, then their largest other amount.
- **CL-3** shows overdue tasks and ownerless tasks as two numbers; the project
  breakdown counts both, the owner breakdown counts overdue only. There's no
  cross-project task list, so it links to Project Health and each project.
- **CL-4 "completed this month"** = Completed projects last updated this month
  (status changes aren't timestamped).
- **DD-3** opens the task panel; it doesn't scroll to the comment yet.
- **SL-1 / SL-2 "Send"** open the invoice with `?send=1`, which opens the
  existing Send dialog (preview, recipients) — no second send flow.
- **Phase 2 cards** (superseded by Phase 2 · M8 below) were empty slots behind `DASHBOARD_PHASE2=true` (the spec's
  `dashboard_phase2` flag, `lib/env.ts`).

## Expenses (2026-10-16, beyond the PRD)

Requested after Phase 1: Finance records the studio's own spending —
subscriptions, utilities (electricity), rent, internet, equipment.

- **Manual entry only**, one row per payment (`expenses`). No recurring
  templates or auto-created rows — amounts like electricity change monthly.
- **Opex / capex** is an explicit column; the form preselects capex for
  "Equipment & hardware" and opex otherwise, but either can be chosen.
- **Access:** Finance and C-Level read, record, edit and delete
  (RLS `expenses_*`); every other role sees nothing, not even the menu.
  `created_by` must be the recorder and can't change (`expenses_guard`).
- **Receipts** (PDF or image, 10 MB) go to the private `receipts` bucket,
  uploaded after the row exists (`/api/expenses/[id]/receipt`, linked under
  RLS) and served via `/api/files/receipts/[id]`.
- **Deleted, not archived:** an expense is a plain record, so a wrong or
  duplicate entry is deleted; the audit log keeps vendor, amount and date.
- **Totals** are per currency (opex, capex, total) — never converted.

## C-Level dashboard (2026-10-16)

Spec: `PRD/Clevel dashboard.md` — replaces CL-1…CL-4 of the overview spec.
Code: `lib/clevel/pure.ts` (math, unit-tested), `lib/clevel/queries.ts`,
`app/(app)/dashboard/clevel/`, inputs on `/business` (Business Data).

- **Operating expenses reuse `expenses`.** The spec's `operating_expenses` /
  `expense_categories` would duplicate the Expenses module (Finance + C-Level,
  one row per payment, fixed categories, opex/capex). Instead `expenses` got an
  optional `project_id` (direct project cost, §5.4). Operating cost = opex
  expenses (foreign currency → estimated IDR) + Xendit fees from `payments`;
  **capex is not in the margin** and is shown apart. "Month without operating
  expenses" = no expense row that month.
- **Retainer fee lives in `project_contracts.retainer_fee_per_month`**, not on
  `projects`, so it has the contract value's visibility (Designer & Dev and HR
  never read it). Edited in the project form for retainers.
- **Access** (`*_clevel` migration, tested in `tests/rls/access.test.ts`):
  people costs HR + C-Level; capacity and utilization targets written by HR
  (and admins, so a studio without HR can set them up), capacity also read by
  PM; revenue targets C-Level; FX rates Finance + C-Level; the two dashboard
  settings keys writable by C-Level besides admins. Margins are computed from
  `person_costs` under RLS, so no other role can produce them.
- **Windows.** Every metric runs over the selected period *up to today*, and
  is compared with the same-length window before it (this month 1–16 Oct vs
  1–16 Sep). Targets are pro-rated to the same days, so "% of target" reads as
  on pace. Costs are pro-rated per day; cost and capacity rows carry their own
  start dates (a profile's created date isn't a hire date).
- **Cost per hour** = monthly cost ÷ that month's available hours; a person
  without capacity (e.g. C-Level logging project time) uses 8 h per workday.
  Hours without a cost mark the project/client margin with `*`.
- **Project margin table** shows revenue, cost and margin *in the period*
  (so the period filter applies everywhere); rate per hour, out-of-scope value
  and projected margin are to date. Projected margin exists for fixed projects
  and retainers with an end date. Client margin = Σ its projects' period margin.
- **Attention rule "margin below"** uses the project's to-date margin, only
  when every hour has a cost.
- **Forecast:** a retainer counts for a month unless the project already has a
  payment request due in it (that one is "scheduled"). Pipeline shows as
  Phase 2.
- **No monthly snapshots yet** (§9 "sebaiknya"): history is computed live from
  the source rows; fine at the studio's size. Historical over-budget uses
  usage up to each month's end with the current budget settings (frozen
  retainer months respected).
- **Charts are monochrome** (design system): actual chart-1, target chart-3 —
  the palette validator passes separation and contrast; it flags chroma and
  lightness band, which the monochrome rule overrides. Identity is also carried
  by mark type (bar vs line) and a legend.
- Every Business Data change is audited with the old and new value
  (Business Data → Change history).

## UI library: Fluid Functionalism (2026-10-19)

Every component, style detail and motion now comes from Fluid Functionalism
(Base UI flavor, rounded, compact, Untitled UI icons, system theme), installed
with `npx shadcn@latest add https://www.fluidfunctionalism.com/r/setup/compact.json --overwrite`
and wrapped in `<FluidRoot>` (`app/providers.tsx`). It supersedes
`docs/DESIGN_STYLE.md` where they differ.

- **Theme tokens** follow Fluid: hairline `--border` (no longer transparent),
  near-black primary, the `--surface-*`/`--shadow-*` ladder, Fluid type scale
  (`text-body`, `text-caption`, …), radius scale. Inter (opsz axis) replaces
  Helvetica. Default theme is now **system**. Odama orange stays only as the
  brand mark (`--brand`, logo, mentions).
- **App shell** is the Fluid inset sidebar (off-canvas collapse with `[`,
  hover peek, drawer below md). The 64px icon rail is gone; Fluid has none.
  The open state persists in Fluid's `sidebar_state` cookie.
- **Replaced:** shadcn button/dialog/select/tabs/tooltip/badge/table/switch;
  dropdown-menu → Fluid Dropdown + MenuItem; cmdk palette → CommandMenu;
  popover+cmdk pickers → Combobox; Radix popover/sheet/checkbox rebuilt on
  Base UI with Fluid surfaces and timing; HeroUI view toggle → Fluid Tabs;
  detail tabs → TabsSubtle. `@heroui/react`, `cmdk`, `radix-ui` removed.
- **No red button:** Fluid has no destructive variant, so confirmations use
  the primary button (the dialog title carries the risk); destructive menu
  rows tint red.
- **Server components never use `Button asChild`:** across the RSC boundary
  the child element arrives lazily during SSR, Fluid's Button renders a
  `<button>` and hydration fails. Use `LinkButton` (client) instead.
- Kept, restyled to Fluid tokens: Calendar (react-day-picker), Chart
  (Recharts), Skeleton, Label, Toaster (sonner).

Still Fluid Functionalism components; only the shell and page chrome changed.

  state — Fluid's hover/active stroke bump (1.5 → 2) no longer shows.

  and Client columns are set at weight 500 via `Column.primary`; every other
  cell stays at 400.
- **CSV/PDF icons:** Untitled UI's free set has no file-type icons, so
  `components/file-type-icons.tsx` draws CSV and PDF glyphs on its 24-grid
  file outline; they live in the `icons` map (`csv`, `pdf`) like any other
  icon. Every CSV export/template button uses `csv`, the invoice PDF uses `pdf`.

## Role dashboards in the C-Level layout (2026-10-20)

Sales, PM, Designer & Developer and HR dashboards follow the C-Level overview:
a full-bleed header, one `SummaryStrip` of KPIs, cards on the grid, tables
edge to edge. PM and Designer & Developer KPIs take a period (`?period=`:
this week by default, this month, last 3 / 6 months) compared with the same
number of days before (`resolveWorkPeriod`, `lib/dashboard/pure.ts`).
"Shots" on the Designer & Developer strip are the tasks they finished on
internal projects. Invoice-list and Sales totals are normalised to IDR at
ECB reference rates (Frankfurter, `lib/fx.ts`, cached 6h) — indicative only;
the C-Level dashboard still uses `fx_reference_rates`.

The Designer & Developer dashboard swaps the hours chart for a calendar of
their work (`?month=`, or `?view=week&week=`), sharing the month grid with HR's calendar
(`components/calendar/month-grid.tsx`): projects with an end date are bars,
open-ended ones (retainers) sit in one "Ongoing" row so they don't fill
every week, and their tasks sit on the due day in the project's hue. The
week view has no hour grid (time entries carry no clock time): project bars
over a column per day with that day's tasks as cards and the hours logged. Beside
it: an 18-week heat calendar of logged hours and recent comments on their
tasks.

## HR dashboard, calendar and leave (2026-10-20, beyond the PRD)

- **HR reads every task.** `app.can_view_tasks` lets HR read all tasks (and
  so sections, comments, collaborators, activity) without being a project
  member, to see each person's to-do and what they're working on. Writing is
  unchanged. This replaces the PRD's "HR sees counts only"; the Projects /
  Tasks screens are still not offered to HR (`perms.viewTasks`).
- **HR calendar is HR's alone** (`hr_events`, `hr_event_exceptions`): not
  C-Level, not admins. Events are all day or timed (wall-clock "HH:MM"),
  repeat weekly or monthly until an optional date; a monthly event on the
  31st falls on a short month's last day. "Only this one" edits and deletes
  are exceptions keyed by the occurrence's series date; changing a series'
  timing drops them. The month grid starts on Sunday, as in the reference.
- **Leave is request + approval** (`leave_requests`): members ask for
  themselves (from the Timesheet), HR or an admin decides — never their own
  request — and both sides are notified (`leave_requested`, `leave_decided`).
  Approval writes a `capacity_overrides` row (kind + `leave_request_id`) so
  utilization counts it; cancelling an approved request removes it, and such
  rows can only change through the request. A half day is a tenth of the
  person's weekly hours (4h without a capacity row).
- **Workload** = estimated hours of open tasks due by Sunday (overdue
  included) against weekly hours less this week's leave; tasks without an
  estimate count zero and are flagged in the tooltip.

## PM dashboard in the HR layout (2026-10-21)

The PM dashboard drops its card grid (PM-1…PM-4 and the team-hours chart)
for HR's shape: the period strip, a month calendar beside a project status
column, then the team table. Approvals, billing and tasks at risk stay on
their own screens; the strip still counts out-of-scope hours waiting and
overdue / blocked / ownerless tasks.

- **Calendar** shows only the projects the PM runs (active / on hold), start
  to end; an open end runs to the grid's last day. Three bars per week; the
  rest are dots in the day that open the day's list. A bar opens the project.
- **Project colour** is `projects.calendar_color` (`hr_event_color`, null =
  a hue from the id), set from the dot in the status list or the calendar's
  colour popover. It's written through `projects_update`, so the project's
  PM, Sales and C-Level may change it; the Designer & Dev calendar uses it too.
- **Standing** (`projectStanding`, `lib/dashboard/pure.ts`): *delayed* past
  the end date or with overdue tasks; *at risk* on a budget warning or over,
  a blocked task, on hold, or ending within 7 days with open tasks; *on
  track* otherwise.
- **Team** = active members of the PM's running projects (the PM aside).
  The chevron lists every running project they're on today (started, not
  completed / archived), other PMs' included. Time and tasks are read under
  RLS, so hours, open tasks and utilization cover the projects the PM is a
  member of; other PMs' rows show "—". Utilization = billable hours this
  week ÷ weekly capacity less leave (`weekCapacityHours`, `lib/hr/pure.ts`).

## Phase 2 · M6 Foundation (2026-10-22, `PRD/PRD_Fase-2.md`)

- **Roles, step by step.** The six `user_role` values stay: they pick the
  dashboard preset and keep driving every Phase 1 policy. Phase 2 adds, on
  `profiles`, a job role (catalogue `job_roles`), division, level 1–5, free
  job title, access (`manager` / `member`; admin stays `is_admin`) and a
  direct manager (`manager_id`, no loops), plus per-person modules in
  `module_grants` (People, Finance, Sales, Studio Report). New tables use
  `app.has_module()` and `app.is_manager_of()` (whole reporting line).
  Existing people were backfilled from their role (C-Level → all modules,
  Finance / Sales / HR → their own; PM and C-Level → manager); a new profile
  gets the same preset by trigger. Admins hold every module.
- **Who changes what.** Job role, division, level, title and manager: the
  People module (HR by default). Access level and modules: admins only. The
  person dialog sends only changed fields; `profiles_guard` decides.
- **Change log** for access and (later) KPI/OKR definitions is
  `activity_log` through `logActivity` — no second audit table.
- **Metric Dictionary** (`lib/metrics/pure.ts`, words in
  `lib/metrics/definitions.ts`, page `/metrics`). One definition each for
  week, logged / billable hours, capacity, utilization, workload, on time,
  margin. Fixes from the PRD review: billable everywhere = client-task time
  not waiting on an out-of-scope decision; capacity = contract hours less
  leave (half days included) and public holidays (`public_holidays`), one
  function for C-Level, PM and HR (`weekCapacityHours` is gone); studio
  utilization counts billable divisions only (Design, Development,
  Project), the rest stays visible per role; workload has its own colour
  (brand) and label, amber when overdue work fills most of it; PM "Team
  hours" says it includes the PM, "Team today" that it doesn't; running
  fixed-price projects show budget burn vs progress instead of margin and
  don't rank in the best/worst margins; the C-Level finance card says it is
  cash basis (decision: cash, PRD open question).
- **Tasks.** `task_types` (Regular, Revision, Bug, Report, Content; the
  People module adds more; the `key` never changes so metrics keep
  matching), `reviewer_id` (anyone active — the reviewer sees and edits the
  task without being on the project), `deliverable_url`,
  `original_due_date` (locked), `approved_at`. Statuses read **In review**
  and **Approved** (values `review`, `done`). `tasks_review_flow`: only the
  reviewer, the project's PM or C-Level approve or send back; the owner may
  pull a task out of review; without a reviewer the project's PM reviews.
  Each submission opens a `review_rounds` row with a one-working-day SLA
  (`app.add_workdays`, Asia/Jakarta, holidays off). Hourly job
  `review-sla` tells the reviewer and the PM once per round (daily on
  Vercel, plan limit).
- **Due dates.** A due date that's set changes only with a reason through
  `due_date_changes`: the PM's own change is approved at once, anyone
  else's waits for the PM (approve / decline). The task trigger refuses a
  move without an approved change in the same transaction.
- **Effective due & on time** (`lib/tasks/pure.ts`): agreed due (first due,
  moved by changes approved before it passed) + the reviewer's working days
  past SLA. On time = approved ≤ effective due; tasks without a due date
  aren't counted. Every dashboard's on-time figure goes through
  `onTimeInputs` (`lib/tasks/timing.ts`). Tasks done before Phase 2 count
  their completion day as the approval.
- **Required fields.** The New task dialog requires type, reviewer, due
  date and an estimate of at least one hour; quick add (title only) still
  works and the task shows "Missing …" until filled — the PRD's ≥ 95 %
  target is measured, not forced.
- **Attendance** (`attendance`): people check in from the Timesheet header
  (in office / remote / off). HR's "Working today" counts check-ins and
  leave, not logged hours. Managers and the People / Studio Report modules
  read it.

## Phase 2 · M7 KPI & OKR (2026-10-22)

- **Metrics are definitions** (`metrics.definition`, schema in
  `lib/kpi/definition.ts`): source (tasks, work-log kinds, projects,
  attendance, timesheet, reviews, ratings, manual), scope (self / team),
  filters, calculation (count, sum, percent — optionally scored per week
  and averaged —, ratio, average per value / week / deliverable, rating,
  composite) and direction. The engine (`lib/kpi/engine.ts`) loads rows
  per source (`lib/kpi/sources.ts`) and aggregates them in pure TS
  (`lib/kpi/pure.ts`), so a new metric needs no deploy. Every metric
  gets its plain sentence and a last-month preview in the builder.
- **One `work_logs` table** for the "Log di OS" sources (shot, content,
  idea, support request, QC record, error, release, testimony, challenge)
  instead of nine tables: kind, tags, link, evidence file (`evidence`
  bucket), value / total for counts and ratios, and a review by the
  person's managers, the project's PM, People or C-Level — never by the
  person. Ideas not answered within 3 working days count anyway.
- **Templates are versioned**: a lineage of versions, Draft → Active (from
  the 1st of next month; the version it replaces is archived) → Archived.
  Active versions and their items are locked by trigger. Templates attach
  to job roles (core + add-ons); a person's own core assignment replaces
  the role's, add-ons stack. Assignment changes start next month.
- **Scoring** follows the PRD table; the score is the weighted average of
  items with data; semester items show as progress inside a month and are
  scored in the semester result. Pro-rata (contract hours ÷ 40 × share of
  the period employed) applies to count targets where more is better
  only — caps (lower is better) don't loosen. Calibration: the first two
  months after a person's first assignment or a template's first version.
  Job role changes aren't tracked as history yet, so a promotion
  calibrates only through its new assignment.
- **Results are snapshots** (`kpi_results`, job `kpi-snapshot` on the 1st,
  plus the half-year on 1 Jan / 1 Jul): items are stored with their
  targets and scores, so editing a metric or template never changes past
  scores. Objections: the person, within 7 days, decided by People.
- **Live KPI pages compute on the system connection** after
  `app.can_view_kpi()` proved access under RLS (the person, their managers
  up the line, People, Studio Report) — the same computation the snapshot
  job runs. Individual rating answers stay hidden from the person rated.
- **Ratings**: raters are the manager, the person (self-assessment, HR
  approves), peers on a shared project that week (tasks or time), a job
  role, or named raters; the guard re-checks the rater, derives the
  average and requires a comment under 3.
- **OKR**: members propose their own, managers for their team, People
  approves; studio objectives come from Studio Report and start approved.
  KR progress from a metric (the first owner, cycle so far), linked tasks
  (approved ÷ linked) or the latest monthly check-in (evidence required in
  the UI). Milestones: owners mark done, the approver confirms. Over 5
  objectives / 5 KRs, a milestone without a definition of done and a
  rating weight above 30 % are warnings, never blocks.
- **Seed**: `pnpm db:seed:kpi` (also run by `pnpm db:seed`) loads
  `prisma/data/kpi-master.json`, exported from the KPI Master sheet: 24
  catalogue metrics plus five team / rubric metrics behind "Internal Team"
  (4 × 15 % team metrics + 40 % rubric), 11 templates, 16 job roles with
  their templates, 4 rating forms with the sheet's rubrics, and the Q4 2026
  cycle (empty — the Q4 OKR content wasn't in the sheet). Seeded people
  without a job role get the one matching their Phase 1 role. Open items
  kept as defaults: Expert Designer idea targets as in the sheet, Creative
  Director on Design Core only, Senior Web Developer / Account Lead / HR /
  Finance with the empty state.

## Phase 2 · M9 Sales (2026-10-22)

- **Pipeline** (`/sales`, replaces Attio): stages carry a category (Open /
  Won / Lost) and a default probability; every report counts by category,
  never by name. The Sales module edits deals and stages, Studio Report
  reads (`app.has_module`). Kanban by stage (drag, or "Move to" for
  keyboards) and a list. `deals_derive` stamps the stage date, takes the
  stage's probability unless the same write sets one, fixes Won at 100 % /
  Lost at 0 %, needs a lost reason, sets and clears the close date;
  `deals_history` writes `deal_stage_history` (system only) with the value at
  each move. A stage with deals can't be deleted, and the pipeline always
  keeps one stage per category. A deal can be deleted only before it has a
  project (a lost deal goes to Lost, so it counts in the win rate).
- **Cards**: total and weighted pipeline in IDR (reference rate, else ECB —
  `idrRateMap`, `lib/fx.ts`, shared with the Finance dashboard), win rate and average deal length
  over deals closed in the last 90 days, new leads this month, overdue
  invoices (same rule as the Sales dashboard's "late": an open invoice with
  a pending request past due), and stale deals.
- **Stale** = an open deal in the same stage for more than
  `sales_stale_days` (default 14, admin setting) — PRD open question.
- **Won → project**: a prospect is first added as a client (code asked,
  `createClientFromDeal`); then the project form opens prefilled (name,
  currency, contract value = deal value) and `createProject(values, dealId)`
  links the deal in the same transaction — the trigger refuses it unless the
  deal is won, and the deal's client then stays fixed.
- **Attio import**: CSV read by column name (Record ID, Deal name, Company,
  Stage, Value, Currency, Owner, Expected close, Lead source, Service type,
  Lost reason, Created at, Closed at; others ignored), preview, skip or
  update by Record ID, under RLS. Companies that aren't clients stay
  prospects; stages must exist.
- **Report** (`/sales/report`): candles from `pipeline_snapshots`, written
  by the `pipeline-snapshot` job at 23:55 WIB — nothing before go-live can be
  rebuilt. The bridge per month (start + new or reopened − won − lost ±
  value changes = end) comes from the stage history; "value changes" is
  the remainder, so the bridge always closes. `pnpm db:seed:sales` loads a
  demo pipeline with backfilled snapshots — dev only.
- **Invoices**: type (DP / term / final, optional) and "paid via" (Xendit,
  bank transfer, Wise, PayPal, other) on the draft. Only Xendit invoices get
  payment links. The rate to IDR on the issue date is stored at first send
  (`fx_rate_at_issue`: reference rate, else ECB); a payment's rate is kept
  with it, and the invoice page shows the FX difference per payment.
- **Payment proofs**: Sales uploads (PDF / image, private `payment-proofs`
  bucket) against a sent, unpaid invoice — the invoice reads **Payment
  submitted** (ahead of Overdue, behind Paid) until Finance decides. Finance
  verifies (it becomes a `payments` row, `source = proof`, matched to its
  request, counted as revenue — cash basis) or rejects with a note (back to
  Sent / Overdue). The guard refuses deciding your own proof, editing a
  decided one, or changing anything but the decision. Queue: Payments → To
  verify, and the Finance module's dashboard widget.
- **Access**: Phase 1 invoice policies stay role-based for writing; the
  Sales, Finance and Studio Report modules also read invoices and payments.

## Phase 2 · M10 Finance (2026-10-22)

- **The Finance dashboard is operational** (the Finance role's preset,

  margins stay on Finance Overview and the C-Level dashboard. The strip:

  matched payments, settled IDR), receivables due this week (pending
  requests due Monday–Sunday, IDR estimate), proofs to verify (with the
  oldest one's age against the PRD's 2-working-day target) and expenses

  calendar. FN-4 "Outstanding by client" is replaced by the aging table.
- **Expenses waiting for approval** (PRD card) isn't shown: expenses have

- **Receivables by client** use the studio aging's buckets (not due, 1–30,

- **Sales sees a sales-only workspace.** No "For you" under the Sales

## Hosting: Supabase Cloud + Vercel (2026-10-26)

- **Production runs on Supabase Cloud and Vercel**, not the self-hosted VPS
  the PRD "Stack & arsitektur" sketched. Production project
  `ytduomlxaozuukwiguar` in `ap-southeast-1` (Singapore), Vercel `sin1`. A
  first project created on 2026-10-23 landed in Seoul by mistake and was
  replaced on 2026-10-26 before any real data. Same code, same
  migrations; only the connection strings and the bucket bootstrap differ.
  `docs/VPS_DEPLOY.md` stays as the legacy alternative. Steps:
  `docs/SUPABASE_SETUP.md` §3.
- **Supavisor pooler, two modes.** Vercel functions are IPv4-only and the
  direct `db.<ref>` host is IPv6, so everything goes through the pooler:
  runtime `DATABASE_URL` in transaction mode (`pgbouncer=true`,
  `connection_limit=10`), migrations through `DIRECT_URL` in session mode.
  `connection_limit=1`, the usual serverless advice, deadlocks this app: a
  page fans out parallel queries and runs system-connection reads while a
  `withRls()` transaction holds a connection, so Prisma's per-process pool
  needs headroom; Supavisor multiplexes those onto the real pool.
  `withRls()` stays correct under transaction pooling because the role and
  the JWT claims are transaction-local settings inside one Prisma interactive
  transaction; the codebase has no session-level `SET`, no advisory lock held
  across statements, and no `LISTEN`.
- **Cloud operations run from a developer machine** via `pnpm cloud:*`
  (`scripts/with-env.mjs` + `.env.cloud`, git-ignored), never from Vercel: the
  script refuses localhost URLs and the default seed password, so `.env` and
  `.env.cloud` cannot be mixed up. Buckets come from `supabase/config.toml`
  through `supabase seed buckets --linked`, so local and Cloud share one
  bucket definition.
- **Legacy JWT API keys**, not the new `sb_publishable_` / `sb_secret_` keys,
  so the same env names work on the CLI stack, Cloud and the legacy VPS.
- **`pnpm test:rls` never touches production.** It drops the `public` and
  `app` schemas of `TEST_DATABASE_URL`; it runs against the local CLI
  database or a separate staging project only (`docs/SUPABASE_SETUP.md` §6).
  Production RLS is trusted because the same migrations passed the suite
  locally and `pnpm cloud:status` confirms they were all applied.
