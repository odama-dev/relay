# Decisions & deviations — Odama OS

Choices made while building Phase 1 (`PRD/PRD-Fase-1-MVP.md`) that aren't
obvious from the code. Newest section last.

## Pivot (13 Oct 2026)

- **Onweekend OS → Odama OS.** The previous Company OS codebase was repurposed:
  its design system, shell and shared components stay; every domain module
  (finance, BI/Hermes, HR external talent, services, engagements, demo DB) and
  all old migrations were removed. Phase 1 starts from an empty database, except
  clients and projects imported from CSV (PRD).

## Data layer & access control

- **Prisma + RLS.** Prisma 6 owns the schema and migrations; the access matrix is
  enforced by Postgres Row Level Security. `withRls()` (`lib/db.ts`) runs each
  user request in a transaction as `authenticated` with the user's JWT claims, so
  the same policies apply to the app and to direct Supabase API calls. The system
  connection (migration owner) bypasses RLS and is reserved for auth, webhooks,
  jobs, notifications and audit (see `CLAUDE.md`).
- **Helpers in a private `app` schema**, not `public`, so PostgREST doesn't expose
  them as RPC. `current_role()` from the PRD is `app.user_role()` — `current_role`
  is a reserved SQL word. `app.uid()` reads `request.jwt.claims` itself, so the
  migrations also run on plain Postgres (roles are created if missing).
- **Column-level secrecy → separate tables.** RLS works per row, but the matrix
  hides *columns*: the contract value (Designer & Dev, HR, other PMs) and the hour
  budget (HR). They live in `project_contracts` and `project_budgets` (1:1 with
  `projects`), each with its own policies.
- **Guards as triggers.** Rules that RLS can't express per column are triggers
  that only bite through RLS (`app.via_rls()`): a user can't change their own
  role/admin flag; only the project's PM reviews out-of-scope work; locked weeks
  can't be edited; a sent invoice can only be voided; deleted comments keep their
  text and record who deleted them.
- **Privileged transitions are system actions after an RLS check.** Issuing an
  invoice number, creating Xendit links, recording payments and applying an
  approved time correction run on the system connection, after the user's right
  to do it was proven under RLS (e.g. the correction review itself is an RLS
  update that only the reviewer can make).
- **Aggregates for health** (usage over everyone's time) are computed on the
  system connection after checking the viewer may read the project's budget —
  Designer & Dev may see health but not other people's time entries.
- **Storage:** private buckets, no storage policies. Files are served only by
  app routes that check access under RLS and redirect to a 60-second signed URL.
  Without Supabase, files go to `./.data/storage` (dev only).
- **PM definitions.** "PM project" = the project's `pm_id`. A user with the PM
  role who is only a member can edit project info (matrix "E (M)") but sections,
  members, task deletion and out-of-scope review belong to the project's PM and
  C-Level (`app.can_manage_project`). PM-role users see every project but only
  the tasks/time/contract value of projects they're on.
- **Sales on tasks:** the matrix gives Sales "L (M)" on section & task, so Sales
  members read tasks and comment but don't create or edit them (M2.2's "all
  members can create" is read together with the matrix).

## M0 — Foundation

- **Invitations are app tokens, not Supabase invite links.** Supabase email OTPs
  expire after at most a day; the PRD wants 7 days. The admin API creates the
  auth user (no password), the app emails its own 7-day link
  (`user_invitations`, only a SHA-256 of the token is stored), and accepting it
  sets the password and activates the profile. Resending revokes older links.
- **Password reset** uses a Supabase recovery link generated by the admin API and
  sent through Resend, so every account email shares one template and sender.
- **Deactivation** sets the profile to `deactivated` (it stops resolving on the
  next request) and bans the Supabase user so no session can refresh.
- **Bootstrap admin:** an `ADMIN_EMAILS` address signing in without a profile
  becomes an active C-Level admin; `scripts/create-admin.mjs` sets one up with a
  password on a fresh environment.
- **Notifications:** `notify()` sends a Slack DM when the user is linked, and
  always writes `notification_log`, which doubles as the in-app inbox (bell). Users
  can mute the work-chatter types; approvals, payments and invoice notices can't
  be muted.

## M1 — Client & Project

- **Project code** is assigned by a trigger under an advisory lock (no duplicate
  numbers under concurrency); kind and client are fixed after creation. A client
  code `INT` is reserved for internal projects.
- **Retainer rollover history** is kept in `retainer_periods`: a settings change
  first freezes every past month with the old settings, and the 1st-of-month job
  freezes the month that just ended. Usage is never frozen — late corrections
  still count. Carry-over from month M uses month M's mode (the mode applies "from
  the current month"), and is never negative.
- **Budget alerts** fire once per threshold per period (`project_alerts`, unique);
  thresholds the project falls back under are re-armed. Checked after every time
  change, budget change, and hourly by the `budget-alerts` job.
- **CSV import** runs on the system connection (admin only, one-off migration).
  Template headers may carry the PRD's `*` marker. Users are created as
  `invited`; "Send invitations" emails them afterwards.

## M2 — Task

- `tasks.position` is a float (fractional ordering) so a drag rewrites one row.
  The same order is used inside kanban columns.
- Comment bodies are `{ text, mentions[] }` — plain text with `@Full Name`
  mentions resolved against project members (longest name first) and light
  inline formatting (`**bold**`, `_italic_`, links) rendered safely. Task
  descriptions are validated Tiptap JSON; images must point at our own storage
  route.

## M3 — Time Log

- `minutes` is the stored unit; durations accept `1h 30m`, `1.5`, `1,5`, `1:30`,
  `90m`, `2 jam`. No minimum unit.
- Week lock is a row in `timesheet_locks` (Monday). Through RLS, entries of a
  locked week can't be created, changed or deleted; corrections are applied by
  the system after the reviewer approves.
- Out-of-scope review fields can only be changed by the project's PM / C-Level
  (trigger); the owner may flag/unflag until it's reviewed.

## M4 — Project Health

- Status: On track below the first threshold, Warning from the first threshold up
  to 100% inclusive, Over budget above 100%. Alerts fire when usage *reaches* a
  threshold.
- The overview sorts by a risk score: status first, then usage, overdue tasks and
  waiting out-of-scope entries.

## M5 — Invoice & Payment

- **Invoice number** is taken on the first send (from `app.next_invoice_number`,
  a row-locked yearly counter) and kept if that send fails, so a retry reuses it.
  Numbers already in use are skipped — e.g. ones issued before Odama OS (PRD open
  question 2: set the starting point by inserting into `invoice_sequences`).
- A draft that already got a number (failed send) can only be voided, never
  deleted, so no number disappears.
- **PDF template** is a parameterized HTML placeholder
  (`components/invoice/invoice-document.tsx`) until the studio's Figma template is
  converted (PRD open question 4). PDFs are printed by headless Chrome and stored
  in the `invoices` bucket.
- **Xendit currency** (open question 1): links are created in the invoice
  currency. `settlement_amount_idr` and the FX rate are filled from the callback's
  settlement fields when Xendit sends them; otherwise they stay empty for Finance
  to review. Confirm with the Xendit account before go-live.
- Without Xendit keys outside production, payment links open `/dev/pay/<id>`, a
  local checkout simulator that posts a correctly signed webhook (incl. a
  "send twice" button for the idempotency check).
- Recipients default to the client's billing email + primary contact. The email
  subject may use `{number}`, filled in at send time.

## Theme (2026-10-16)

- The app is no longer dark-only. Light is the default; each user can pick
  Light / Dark / System in the sidebar account menu (next-themes, stored in
  localStorage as `odama-theme`). Both themes use the existing `:root` / `.dark`
  tokens, and design QA now covers both.

## Dashboard per role (2026-10-16)

Spec: `PRD/OVERVIEW-SPEC.md`. `/dashboard` is the home screen (`/` redirects
there); the card set follows `profiles.role`, `is_admin` doesn't change it.

- **Queries in app code, under RLS — not views.** The spec suggests database
  views / RPCs for the heavy aggregates. Every card instead reads through
  `asUser` (`lib/dashboard/queries.ts`), so the same policies apply; health
  reuses `computeHealth` after the budgets were read under RLS, exactly like
  Project Health. The one exception is **HR-3 (tasks per person)**: HR can't read
  tasks, so `app.task_summary_per_person()` (migration `…_dashboard`, `SECURITY
  DEFINER`) returns counts only, and only to HR, C-Level and admins — tested in
  `tests/rls/access.test.ts`.
- **One slot per card.** Each card (`app/(app)/dashboard/card.tsx`,
  `defineCard`) has its own Suspense skeleton and turns a failed load into its
  error state with "Try again", so one card never takes the page down.
- **Past workdays only.** DD-2 and HR-1 flag workdays *before today* without
  time ("hari kerja yang sudah lewat"); the compliance page (M3.7) still counts
  today.
- **Currencies are never converted**, so where the spec says "largest" across
  currencies: CL-1 lists the 5 *longest-overdue* requests, and FN-4 ranks clients
  by their IDR amount, then their largest other amount.
- **CL-3** shows overdue tasks and ownerless tasks as two numbers; the project
  breakdown counts both, the owner breakdown counts overdue only. There's no
  cross-project task list, so it links to Project Health and each project.
- **CL-4 "completed this month"** = Completed projects last updated this month
  (status changes aren't timestamped).
- **DD-3** opens the task panel; it doesn't scroll to the comment yet.
- **SL-1 / SL-2 "Send"** open the invoice with `?send=1`, which opens the
  existing Send dialog (preview, recipients) — no second send flow.
- **Phase 2 cards** are empty slots behind `DASHBOARD_PHASE2=true` (the spec's
  `dashboard_phase2` flag, `lib/env.ts`).

## Expenses (2026-10-16, beyond the PRD)

Requested after Phase 1: Finance records the studio's own spending —
subscriptions, utilities (electricity), rent, internet, equipment.

- **Manual entry only**, one row per payment (`expenses`). No recurring
  templates or auto-created rows — amounts like electricity change monthly.
- **Opex / capex** is an explicit column; the form preselects capex for
  "Equipment & hardware" and opex otherwise, but either can be chosen.
- **Access:** Finance and C-Level read, record, edit and delete
  (RLS `expenses_*`); every other role sees nothing, not even the menu.
  `created_by` must be the recorder and can't change (`expenses_guard`).
- **Receipts** (PDF or image, 10 MB) go to the private `receipts` bucket,
  uploaded after the row exists (`/api/expenses/[id]/receipt`, linked under
  RLS) and served via `/api/files/receipts/[id]`.
- **Deleted, not archived:** an expense is a plain record, so a wrong or
  duplicate entry is deleted; the audit log keeps vendor, amount and date.
- **Totals** are per currency (opex, capex, total) — never converted.

## C-Level dashboard (2026-10-16)

Spec: `PRD/Clevel dashboard.md` — replaces CL-1…CL-4 of the overview spec.
Code: `lib/clevel/pure.ts` (math, unit-tested), `lib/clevel/queries.ts`,
`app/(app)/dashboard/clevel/`, inputs on `/business` (Business Data).

- **Operating expenses reuse `expenses`.** The spec's `operating_expenses` /
  `expense_categories` would duplicate the Expenses module (Finance + C-Level,
  one row per payment, fixed categories, opex/capex). Instead `expenses` got an
  optional `project_id` (direct project cost, §5.4). Operating cost = opex
  expenses (foreign currency → estimated IDR) + Xendit fees from `payments`;
  **capex is not in the margin** and is shown apart. "Month without operating
  expenses" = no expense row that month.
- **Retainer fee lives in `project_contracts.retainer_fee_per_month`**, not on
  `projects`, so it has the contract value's visibility (Designer & Dev and HR
  never read it). Edited in the project form for retainers.
- **Access** (`*_clevel` migration, tested in `tests/rls/access.test.ts`):
  people costs HR + C-Level; capacity and utilization targets written by HR
  (and admins, so a studio without HR can set them up), capacity also read by
  PM; revenue targets C-Level; FX rates Finance + C-Level; the two dashboard
  settings keys writable by C-Level besides admins. Margins are computed from
  `person_costs` under RLS, so no other role can produce them.
- **Windows.** Every metric runs over the selected period *up to today*, and
  is compared with the same-length window before it (this month 1–16 Oct vs
  1–16 Sep). Targets are pro-rated to the same days, so "% of target" reads as
  on pace. Costs are pro-rated per day; cost and capacity rows carry their own
  start dates (a profile's created date isn't a hire date).
- **Cost per hour** = monthly cost ÷ that month's available hours; a person
  without capacity (e.g. C-Level logging project time) uses 8 h per workday.
  Hours without a cost mark the project/client margin with `*`.
- **Project margin table** shows revenue, cost and margin *in the period*
  (so the period filter applies everywhere); rate per hour, out-of-scope value
  and projected margin are to date. Projected margin exists for fixed projects
  and retainers with an end date. Client margin = Σ its projects' period margin.
- **Attention rule "margin below"** uses the project's to-date margin, only
  when every hour has a cost.
- **Forecast:** a retainer counts for a month unless the project already has a
  payment request due in it (that one is "scheduled"). Pipeline shows as
  Phase 2.
- **No monthly snapshots yet** (§9 "sebaiknya"): history is computed live from
  the source rows; fine at the studio's size. Historical over-budget uses
  usage up to each month's end with the current budget settings (frozen
  retainer months respected).
- **Charts are monochrome** (design system): actual chart-1, target chart-3 —
  the palette validator passes separation and contrast; it flags chroma and
  lightness band, which the monochrome rule overrides. Identity is also carried
  by mark type (bar vs line) and a legend.
- Every Business Data change is audited with the old and new value
  (Business Data → Change history).

## UI library: Fluid Functionalism (2026-10-19)

Every component, style detail and motion now comes from Fluid Functionalism
(Base UI flavor, rounded, compact, Untitled UI icons, system theme), installed
with `npx shadcn@latest add https://www.fluidfunctionalism.com/r/setup/compact.json --overwrite`
and wrapped in `<FluidRoot>` (`app/providers.tsx`). It supersedes
`docs/DESIGN_STYLE.md` where they differ.

- **Theme tokens** follow Fluid: hairline `--border` (no longer transparent),
  near-black primary, the `--surface-*`/`--shadow-*` ladder, Fluid type scale
  (`text-body`, `text-caption`, …), radius scale. Inter (opsz axis) replaces
  Helvetica. Default theme is now **system**. Odama orange stays only as the
  brand mark (`--brand`, logo, mentions).
- **App shell** is the Fluid inset sidebar (off-canvas collapse with `[`,
  hover peek, drawer below md). The 64px icon rail is gone; Fluid has none.
  The open state persists in Fluid's `sidebar_state` cookie.
- **Replaced:** shadcn button/dialog/select/tabs/tooltip/badge/table/switch;
  dropdown-menu → Fluid Dropdown + MenuItem; cmdk palette → CommandMenu;
  popover+cmdk pickers → Combobox; Radix popover/sheet/checkbox rebuilt on
  Base UI with Fluid surfaces and timing; HeroUI view toggle → Fluid Tabs;
  detail tabs → TabsSubtle. `@heroui/react`, `cmdk`, `radix-ui` removed.
- **No red button:** Fluid has no destructive variant, so confirmations use
  the primary button (the dialog title carries the risk); destructive menu
  rows tint red.
- **Server components never use `Button asChild`:** across the RSC boundary
  the child element arrives lazily during SSR, Fluid's Button renders a
  `<button>` and hydration fails. Use `LinkButton` (client) instead.
- Kept, restyled to Fluid tokens: Calendar (react-day-picker), Chart
  (Recharts), Skeleton, Label, Toaster (sonner).

### Flat shell, Attio-style (2026-10-19)

Still Fluid Functionalism components; only the shell and page chrome changed.

- **Shell:** Fluid sidebar `variant="sidebar"` on a flat grey `--sidebar`
  with a hairline edge, beside a square white content area (no inset card,
  no radius, no shadow). Brand row and the content topbar share one 48px
  hairline strip; the topbar shows the current section crumb.
  No hover peek: the collapsed trigger only shows its tooltip and
  expands on click (`peek="none"`).
- **Search + inbox** sit side by side at the top of the rail. The inbox opens
  to the right of the rail with a soft `shadow-overlay`.
- **Page chrome:** list pages stack edge-to-edge rows split by hairlines —
  compact `PageHeader`, `SummaryStrip`, `FilterBar` (toolbar) — and a
  page-level `DataTable` bleeds to the content edge (`--page-gutter`,
  `.bleed`). Full `PageHeader` is a bold 22px title closed by a hairline
  (or by the tab row's hairline when `EntityTabs` follows). Consecutive
  `FormSection`s are split by hairlines.
- **Centred pages:** Settings, Profile and People (member management) sit in a
  centred container; People uses the inline `FilterBar` + bordered table.
- **Fields are white:** inputs, selects, comboboxes, date pickers and the
  tertiary button use `--field` (white; raised grey in dark) + `shadow-field`
  instead of a transparent fill.
- **Tables are grids (2026-10-19):** every list table (`DataTable`,
  `gridTableClass` for hand-built tables) runs edge to edge of the content
  area with no container padding — first/last column text sits on the page
  gutter — one hairline under each row, hairlines between columns, a
  full-row hover tint (no floating Fluid highlight). Inside a DashboardCard
  the table runs to the card's edges (`--page-gutter: 1rem`).
- **One line per cell (2026-10-19):** no stacked two-line cells anywhere —
  `CellStack` is gone; a second fact (code, client, role, email, issue date,
  approved OOS hours) gets its own column, and cells never wrap
  (`gridTableClass` sets `whitespace-nowrap`; wide tables scroll sideways).
- **Project status in tables is a dot:** no Status column on project tables;
  `StatusDot` (`components/status-badge.tsx`) sits left of the project name
  in the status' hue and names it in a tooltip on hover/focus.
- **One icon weight:** every 24-grid outline icon renders at `--icon-stroke`
  (1.25px) via a non-scaling stroke in `globals.css`, whatever its size or
  state — Fluid's hover/active stroke bump (1.5 → 2) no longer shows.
- **Project column is medium (2026-10-19):** in every table the Project
  and Client columns are set at weight 500 via `Column.primary`; every other
  cell stays at 400.
- **CSV/PDF icons:** Untitled UI's free set has no file-type icons, so
  `components/file-type-icons.tsx` draws CSV and PDF glyphs on its 24-grid
  file outline; they live in the `icons` map (`csv`, `pdf`) like any other
  icon. Every CSV export/template button uses `csv`, the invoice PDF uses `pdf`.
